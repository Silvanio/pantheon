## Context

Pantheon's authorization model is entirely imperative — no `@PreAuthorize` exists anywhere in `pantheon-service`; every gate is a hand-written `requireX(id, userId)` method inside a service (`CompanyService.requireMembership`/`requireAdmin`, `ConstructionSiteService.requireMembership`/`requireAdmin`, `SiteAccessService.resolve`). The JWT principal set by `JwtAuthenticationFilter` is the plain `AppUser` entity itself (not a wrapper), and `SitePermissionService.resolve()` already grants unconditional `MANAGE` on every capability whenever `SiteAccessContext.companyStaff()` is true. This meant a platform-superadmin bypass could be added as a single conditional at the top of three existing gate methods, reusing 100% of the existing downstream permission machinery, rather than introducing a new authorization mechanism.

## Goals / Non-Goals

**Goals:**
- A superadmin needs zero `CompanyMembership`/`SiteMembership` rows to see and manage every company and every obra.
- Reuse the existing `Page<T>`/`page`/`size` pagination convention (already used by all four list endpoints) for the new company-listing endpoint, and reuse it in the frontend for the page-size selector — no new pagination primitive.
- Fix the tab-reset bug at its root (the tab was never part of the URL) rather than special-casing each back button.
- One shared checkbox class, not a per-page fix.

**Non-Goals:**
- A UI for granting/revoking superadmin status — the flag is seeded directly via migration for now; no admin-managing-admins screen.
- Any change to `pantheon-mobile` — none of the four items were requested for mobile, and mobile's own list screens already deliberately skip real pagination (a single generously-sized fetch), which this change doesn't touch.
- Editing/removing existing checked items from a list (the checkbox styling change is purely visual — no interaction semantics changed).

## Decisions

- **Superadmin bypass lives inside the three existing gate methods, not as a new authorization layer.** `SiteAccessService.resolve()` checks `PlatformAdminService.isSuperAdmin(userId)` first and returns the same `SiteAccessContext(true, null)` shape company staff already get; `CompanyService`/`ConstructionSiteService`'s `requireMembership`/`requireAdmin` return early the same way. This is the smallest change that gets a superadmin full read/manage access everywhere permission-gated code already exists, verified end-to-end against the real dev database (company list, a company's obras/staff/settings, and a specific obra's full summary all returned real data with zero membership rows for the seeded superadmin).
- **`superAdmin` is embedded in the JWT as a display/routing hint only**, exactly like the existing `email` claim's documented "never trust this for authorization" contract — every server-side check still re-reads the flag fresh from `AppUser` via `PlatformAdminService`, never from the token.
- **No Company/CompanyMembership row for the superadmin account.** The user explicitly retracted an earlier plan to seed a placeholder "Inext" company with a CNPJ — a superadmin belongs to no company, and the frontend router guard special-cases `isSuperAdmin` before any of the company-onboarding logic runs, sending them straight to `/admin` instead of "create a company".
- **Page-size selector is `[1, 5, 10]`**, matching the user's literal request, not the more typical `[10, 25, 50]` — a deliberate small-numbers choice for this app's obra-scoped lists, which rarely have more than a few dozen rows.
- **The size selector is always visible once the list is non-empty**, independent of whether there's currently more than one page — so choosing a smaller size is how a user discovers there's now more than one page, not something only available once pagination is already showing.
- **Breadcrumb fix seeds `activeTab` from `route.query.tab` in `SiteDetailView`'s existing `load()`**, rather than keeping the URL in sync on every in-page tab click — the bug only manifests on a fresh mount (arriving via a link from outside the page), so only the initial read needed to change. A `SiteBreadcrumb.vue` component (site name link + section link carrying `?tab=`) replaces each detail view's back button; post-delete redirects (`router.back()`) were switched to explicit pushes to `/sites/:id?tab=:tab` for the same reason.
- **One `.field-checkbox` class using `accent-color`**, not a custom-built checkbox (no extra markup/JS, no `@tailwindcss/forms` dependency) — modern browser support for `accent-color` is sufficient for this app's target browsers, and it was confirmed visually correct in both light and dark mode via a live screenshot.
- **Breadcrumb moved into `AppHeader`'s `#left` slot, with a leading back-arrow icon**, after a follow-up request — the breadcrumb previously lived inline at the top of `<main>`; header placement matches where the back button it replaced used to live, and the icon gives a one-click "go back" affordance without abandoning the breadcrumb trail (the icon's target is identical to the section crumb's, not a browser-history `router.back()`, so it's exempt from the original bug it's fixing).
- **Global Tasks Board obra filter is entirely client-side, no new backend endpoint.** The board's own load already fetches every obra's cards for the company in one call; obra counts per company are modest (single digits to low tens in observed data), so fetching the full obra list once (`listSites(companyId)`, already used elsewhere) and filtering/capping to 10 in a computed property is simpler and cheaper than adding a paginated, searchable sites endpoint purely for this dropdown — unlike the superadmin company picker, which genuinely needed server-side paging since it lists across every company on the platform.
- **Fixed a superadmin-bypass gap found during this work's own live verification**: `GlobalTaskBoardService` had a private `requireAdmin` duplicating `CompanyService`'s membership check inline, rather than delegating to it — so the earlier superadmin bypass (added to `CompanyService`/`ConstructionSiteService`/`SiteAccessService`) never reached it. Patched the same way as the other three, rather than refactoring `GlobalTaskBoardService` to delegate to `CompanyService` (a larger, riskier change out of scope here).
- **Global board's assignee names are resolved server-side and returned as a company-wide `assignees` list, not left to the frontend to fetch per-site.** The per-obra board (`TaskCardService`/`TasksBoardPanel.vue`) resolves names client-side because it only ever deals with one site's memberships (a single `listMembers(siteId)` call). The global board aggregates cards from every obra of the company at once, so resolving names client-side would mean one `listMembers` call per distinct site touched by any card — instead, `GlobalTaskBoardService` resolves every referenced site-membership id in one batch (`SiteMembershipRepository.findAllById` + `AppUserRepository.findAllById`), reusing `SiteMembershipService.listMembers`'s exact name-fallback logic (linked `AppUser`'s display name, else the accountless membership's own stored name) so an assignee who's a service-provider-with-no-account still resolves correctly.
- **Reused the existing `TaskCardAssigneeRepository`/`TaskCommentRepository`/`SiteDocumentProjectAttachmentRepository` count-by-card-ids methods unchanged** — none of them are scoped to a single site already, they just take a `List<UUID> cardIds`, so feeding them the full cross-site card-id list works with zero repository changes.
- **Breadcrumb split into three levels after a follow-up bug report**: the single "section" crumb (e.g. "Pedido de Compra") was ambiguous — it read as "you are here" while actually being a link back to the list. `SiteBreadcrumb.vue` now renders obra name → "Lista de {label}" (a real link back to the list, i18n key `common.breadcrumb.list`) → a final, non-clickable `{label}` segment marking the current detail page as distinct from the list it came from. The back-arrow icon and the "Lista de..." link both still target the same `?tab=` destination as before — only the labeling and the addition of the non-clickable leaf changed.

## Risks / Trade-offs

- [Risk] A superadmin's very broad bypass (full `MANAGE` on every capability of every obra, of every company) has no audit trail beyond normal request logging. [Mitigation] Out of scope for this change; flagged here for future consideration (e.g. an audit log keyed on `AppUser.superAdmin`-gated actions) rather than silently deferred.
- [Risk] Seeding a real password hash directly in a SQL migration means the password is fixed at deploy time and only changeable via a new migration or a future "change password" flow. [Mitigation] Acceptable for this initial seed — the account's credentials were explicitly supplied by the user for this purpose.
