## Context

`pantheon-mobile` already has a solid offline-support foundation from `fix-mobile-permission-parity-and-offline-support` (archived): `ApiClient.get` caches every GET by default into a sqflite `cache` table and falls back to it only on a connectivity error (network-first, cache-as-fallback — already matches "online → always fetch fresh; offline → read local"); an `OutboxController` drains a sqflite `outbox` table of queued mutations on the connectivity offline→online transition or a manual "Sincronizar agora."

That design's own Risks section already named the bug being fixed here: Riverpod's `FutureProvider`/`FutureProvider.family` keep a screen's last `AsyncValue` — including an error — forever once built, across navigations, with pull-to-refresh as the only escape hatch. Confirmed by direct audit: zero uses of `.autoDispose` anywhere in `lib/`. Two concrete instances were found:
- **First login**: nothing invalidates data providers after `AuthController.login()` succeeds. A provider built (and possibly errored, e.g. racing token availability) before or during login stays in that state indefinitely — `login_screen.dart` never calls `ref.invalidate`/`ref.refresh` on anything.
- **Cross-navigation staleness**: `daily_report_detail_screen.dart`'s submit/approve/reject flows invalidate only `_detailProvider(widget.id)`, never the sibling `dailyReportListProvider(siteId)` — returning to the list shows the pre-submit status. This is structural (any screen's mutation can miss a sibling elsewhere), not a one-off typo.
- **Found during implementation, not anticipated at design time**: `.autoDispose` alone does not fix the "list → open an item → edit/submit → back to list" flow, which is the app's single most common navigation pattern. `context.push` (used everywhere a list opens a detail screen) keeps the pushed-FROM screen's widget mounted underneath the whole time it's obscured by the pushed-TO screen — it is not popped, so its `ref.watch` never stops, the provider's watcher count never reaches zero, and `.autoDispose` never tears it down. Only a full pop-then-different-push (e.g. leaving the site entirely and re-entering) exercises `.autoDispose`'s teardown path. Confirmed live in the iOS Simulator: after converting providers to `.autoDispose` alone, submitting a report from its detail screen and pressing back still showed the old status in the list; a report created directly via the API while the app sat on a *different, fully-popped-back-to* screen *did* show up correctly, isolating the gap to the push/pop case specifically. See the added Decision below.

Separately: the accepted spec's wording says a "qualifying write" for Diário de Obra includes "create/submit," but reading `DailyReportRepository`/`PurchaseRequestRepository` in full shows this was never actually the intent — `submit`/`approveStep`/`rejectStep` (and `conclude` for Pedido de Compra) are explicitly commented as "the approval workflow itself... never queued," and every structural edit to an already-existing record (`updateCore`, workforce/equipment/activity add-delete, `addItems`/`removeItem`) is explicitly commented as requiring connectivity because it "mutates an existing record other screens may already be showing, so silently queueing it offline risks the UI looking out of sync with what's actually on the server." Only `create` (a brand-new record, nothing else can be showing it yet) and photo/video upload (the literal "flaky signal in the field" case) are queued. This is a deliberate, already-reasoned, and correct scope — the spec's wording is simply imprecise about it, not the code. No repository code change is warranted; the spec text gets corrected to match the code instead.

## Goals / Non-Goals

**Goals:**
- A screen always shows a fresh fetch (network-first, cache-fallback-if-offline) when the user navigates to it, never a stale `AsyncValue` left over from a previous visit.
- Logging in, logging out, or switching users on a shared device never shows a previous session's cached screen state, even transiently.
- The spec's description of what's queued offline accurately reflects the app's actual, already-correct behavior.

**Non-Goals:**
- No change to `ApiClient`'s cache-fallback mechanism, `OutboxController`'s sync-drain triggers, or the `requireOnline`/`confirmProceedOffline` dialogs — all already correct.
- No change to which mutations are queued vs. require connectivity — that scope is already correct and deliberate (see Context); this change does not touch `DailyReportRepository` or `PurchaseRequestRepository`.
- No expansion of offline support to Tasks, Projetos, Permissões, or either feature's approval workflow — unchanged Non-Goals.
- No conflict resolution for concurrent edits — unchanged from the original design; still out of scope.
- No new local-storage technology or schema change to the `cache`/`outbox` tables.

## Decisions

- **Convert screen-data providers to `.autoDispose`/`.autoDispose.family`, full stop, as the primary fix.** When nothing is watching a provider (the user has navigated away from the screen that reads it), Riverpod tears it down; returning to that screen re-runs its build function from scratch, which calls the repository, which calls `ApiClient.get` — network-first, exactly the "online → always fetch fresh" policy the user wants, with cache-fallback if offline. This needs no hand-maintained "which sibling providers does this mutation affect" registry (the actual bug found in daily-report submit/approve/reject): the list screen's provider is simply gone by the time you mutate something on the detail screen, so returning to it fetches fresh unconditionally. **Explicitly NOT converted**: `outboxControllerProvider`, `authControllerProvider`, `offlineDbProvider` — these are app-wide singletons that must survive the whole session regardless of what's currently on screen.
  - *Alternative considered*: keep providers non-autoDispose and instead build a manual invalidation map (mutation → list of provider keys to invalidate). Rejected — this is exactly the "bagunçado," easy-to-forget-a-case pattern that already caused the daily-report list bug, and it grows one entry per new screen relationship forever. `autoDispose` makes correctness the default instead of something each new feature has to remember.
  - *Alternative considered*: `ref.keepAlive()` on every provider with a manual TTL/refresh timer. Rejected — adds a timer/expiry concept the app doesn't need; "gone when unwatched, fresh when watched again" is simpler and maps directly onto "the user navigated away and came back."
- **A `sessionEpochProvider` (`StateProvider<int>`, bumped in `AuthController` on successful login and on logout/forced-logout) that every screen-data provider's build function reads first** (`ref.watch(sessionEpochProvider)`, value otherwise unused), as defense-in-depth alongside `autoDispose` specifically for session isolation on a shared device. `autoDispose` alone only guarantees freshness when a provider's watcher count actually reaches zero during the transition; a bump-on-auth-change guarantees every screen-data provider recomputes at the moment of login/logout regardless of whatever navigation/widget-tree timing happens to hold a watcher alive across that transition — construction sites routinely share one tablet/phone between workers, so this is a real correctness requirement, not just defensive style.
  - *Alternative considered*: manually enumerate every data provider and `ref.invalidate` it in `AuthController`. Rejected for the same "grows forever, easy to miss one" reason as the sibling-invalidation alternative above — the epoch makes opting in a one-line addition to a provider's own build function, at the provider's own definition site, instead of a list maintained somewhere else that drifts out of sync.
- **A `RefreshOnReturn` mixin (`lib/core/widgets/refresh_on_return.dart`), built on Flutter's `RouteAware`/`RouteObserver`, complements `.autoDispose` for the push/pop case.** A screen mixes it in and implements `onReturnVisible()`; the mixin subscribes to a shared `routeObserver` (registered on `GoRouter`'s `observers`) and calls `onReturnVisible()` on `didPopNext` — i.e. exactly when a route pushed on top of this screen is popped and this screen becomes visible again. Applied to `DailyReportListScreen`, `PurchaseRequestListScreen`, and `SiteHomeScreen` (whose own stat cards/status have the identical staleness risk from pushing into any of its entries and coming back), each invalidating its own provider(s). This required converting those three from `ConsumerWidget` to `ConsumerStatefulWidget` to get a `State` to mix into.
  - *Alternative considered*: skip this and rely on `.autoDispose` alone, accepting that only "leave the site and come back" refreshes a list, not "open an item and come back." Rejected — this is precisely the navigation pattern the user's original bug report described, and precisely how the app is used in practice.
  - *Alternative considered*: keep the existing per-mutation manual `ref.invalidate(siblingProvider)` calls (already present for e.g. delete-then-pop in `purchase_request_detail_screen.dart`) instead of a general mechanism. Rejected for the same "easy to add a ninth mutation and forget the tenth" reason `.autoDispose` itself was chosen over a manual invalidation map — `onReturnVisible` is written once per screen, at the screen's own definition, and covers every current and future way something pushed on top of it could change its data, not just the ones anticipated today. Existing manual invalidate-after-delete calls are left in place as harmless, redundant defense-in-depth rather than removed.
  - Not applied to every screen with an `.autoDispose` provider — only ones that (a) push to a sub-screen capable of mutating data the parent displays, and (b) stay mounted underneath during that push. Screens whose only mutations happen via bottom sheets/dialogs (which don't push a new route, so never unmount the underlying screen in the first place — nothing to "return" to) don't need it, e.g. `MaterialListScreen`'s mark-delivered flow.
- **Correct the spec's wording, leave the code alone.** The spec's "qualifying write" list is edited to say what the code actually and correctly does (create a report, create a purchase request, upload a photo/video — nothing else) instead of the inaccurate "create/submit." Reopening the already-reasoned decision to exclude submit/approve/reject/conclude/structural-edits from queueing was considered and rejected: the existing in-code rationale (queueing a mutation to an already-visible-elsewhere record risks the UI looking out of sync with the server) is sound and this change has no new information that would overturn it.

## Risks / Trade-offs

- [Re-entering a screen now always shows a brief loading state instead of instantly re-displaying the last-known value while quietly refreshing] → this is the correct trade-off (freshness over false instancy — the actual bug being fixed is stale data being shown instantly with confidence), but check `lib/core/widgets/async_value_view.dart` during implementation and, if the loading flash feels jarring in practice, consider distinguishing "first-ever load" from "refetch after remount" there — not a blocking design decision, a visual-polish follow-up if needed.
- [A provider that some screen legitimately expects to survive a same-route dialog/bottom-sheet interaction (e.g. `showModalBottomSheet`) could see unwanted extra fetches if converted] → Flutter's `showDialog`/`showModalBottomSheet` don't unmount the underlying route, so the screen's own `ref.watch` stays live and the provider is never disposed during that interaction — verified this is how the app's existing sheets (media detail, add-media staging) work, so this risk doesn't materialize in practice, but worth a spot-check per screen during implementation.
- [`StateProvider` for the epoch is intentionally the simplest possible primitive] → if a future need arises for the epoch to carry more than a counter (e.g. the actual user id, to detect same-user re-login vs. different-user login), it can be widened later without changing the dependency pattern (providers already just `ref.watch` it for its change-notification, not its value).

## Migration Plan

Pure refactor on the mobile app: no new dependency, no `cache`/`outbox` schema change, no backend or web change, no repository code touched. `GoRouter`'s `observers` list gains one entry (`routeObserver`), additive and non-breaking alongside the existing `SentryNavigatorObserver`. Deploy as a normal mobile app version bump. Rollback is reverting the mobile app version; nothing persisted needs cleanup since the local DB schema is untouched.

## Open Questions

None. The provider-conversion list was fully enumerated from a direct grep audit, the outbox-scope question was resolved during design (no code change needed), and the push/pop gap this section originally missed was caught by live-testing the fix in the iOS Simulator against the reproduction steps in the bug report — rather than assuming `.autoDispose` was sufficient — before considering this design final. That verification is what surfaced the need for `RefreshOnReturn`.
