## Why

Diário de Obra's current UI is a long stack of independently-saved sections, several sub-resources are manual free text with no link to data that already exists elsewhere in the app (registered equipment, delivery-tracked materials), mobile is missing entire sections the web has, and the "Assinaturas" block is dead weight now that a real approval workflow exists. The user reviewed a visual redesign (mockup approved) and wants it implemented faithfully across `pantheon-service`, `pantheon-web`, `pantheon-mobile`, and the PDF export.

## What Changes

- **Global save UX** (web/mobile): one "Salvar alterações" action instead of a save button per section. This is a client-side orchestration change — the existing per-section endpoints stay (see design.md Decision 1) — the UI stages edits locally and fires the necessary calls together when the user saves, with a "tudo salvo"/dirty indicator.
- **Mão de obra**: a team-member picker (already exists on web, missing on mobile — build it there) becomes the primary path, kept alongside free-text "outra mão de obra" entries (already supported by the existing nullable `membershipId` field — no schema change). New: a delete endpoint for a workforce entry, so a row can be removed after it's been added.
- **Equipamentos**: the daily-report equipment picker reuses the registry's existing name/type/status filter (already built for the Equipamentos tab, just not wired into this picker) instead of loading all 200 unfiltered. **Schema change**: `DailyReportEquipmentUsage.equipmentId` becomes nullable, with a new `customName` field, so "outro equipamento" (not registered) can be logged the same way workforce already supports an unregistered person. New: a delete endpoint for an equipment-usage entry.
- **Atividades**: `description` is already required (`@NotBlank`) — no backend change needed, just carry it into the new UI. New: a delete endpoint for an activity.
- **Materiais recebidos — two sections, not a replacement** (per explicit user decision): the existing manual entry (`DailyReportMaterialReceived`, free text, never touches the `Material` delivery-tracking registry) **stays exactly as it is today**, and a **new**, separate, read-only section is added showing `Material` records (created when a Pedido de Compra is concluded) whose `deliveredAt` falls on this report's `reportDate` for this construction site — each showing its delivered/delivered-and-checked status and a link back to its source Pedido de Compra, with a "marcar conferido" action that calls the existing `MaterialService.markChecked` (so it's the same underlying record the Materiais tab already shows — no duplicate status system).
- **Mídia & Anexos**: drag-and-drop multi-file upload on web (new — no existing pattern in the app to mirror, built from scratch on the native HTML5 drag/drop events, calling the existing upload endpoints); per-photo/video caption becomes editable after upload (new PATCH endpoints — media/attachments currently have no update or delete endpoint at all, both are added); on mobile, adding several photos before saving reuses the staged multi-photo bottom sheet pattern already built for the Materiais feature this session. **New**: Pedido de Compra "nota fiscal" (`PurchaseRequestInvoice`) attachments uploaded **today** (matching the invoice's own upload date to the report's date, regardless of which day the underlying Pedido de Compra itself is from) appear automatically in the Diário's Anexos list, referencing their source Pedido de Compra — read-only, not a copy.
- **Aprovação replaces Assinaturas**: the "Assinaturas" (`DailyReportSignature`) UI block is removed from the web (mobile never had one). The backend entity/endpoints are **not deleted** — only unused by the UI for now, since sign-off may come back later (see design.md Decision 5). The existing approval history becomes the report's closing section, and `decidedBySiteMembershipId` is resolved to a display name (currently shown nowhere, not even as a raw id) in the API response, the web/mobile UI, and the PDF.
- **Visual redesign**: web, mobile, and the PDF export are restyled to match the approved mockup, staying inside the existing design system (`blueprint-*`/`steel-*`/`safety-*` tokens, Manrope, `.card`/`.btn-*` classes — see `openspec/specs/obra-visual-design/spec.md`); PDF keeps its existing Helvetica/Arial-not-Manrope convention (`PdfBrandingService.STYLE`'s documented trade-off) while adopting the same section language (icon+title cards, the "Aprovações" table).
- **BREAKING**: none of the above removes or changes the meaning of an existing API field except `DailyReportEquipmentUsage.equipmentId` becoming nullable (widening, not narrowing — existing rows are unaffected).

## Capabilities

### Modified Capabilities
- `daily-construction-report`: workforce/equipment/activity gain delete endpoints; equipment usage supports an unregistered "outro equipamento" entry; the equipment picker filters like the registry does; a new read-only "materials delivered on this date" view is added alongside (not replacing) manual materials-received entry.
- `daily-report-media-and-signoff`: media/attachments gain update (caption) and delete endpoints and expose their upload timestamp; Pedido de Compra invoices uploaded on the report's date are surfaced in its Anexos list; the "Report sign-off" UI is removed from `pantheon-web` (backend requirement is unchanged — sign-off still works if called directly, it's just not exposed in this UI anymore).
- `daily-report-approval-workflow`: approval steps' `decidedBySiteMembershipId` is resolved to a display name in the API response.

## Impact

- **Affected code**: `pantheon-service` — `DailyReportEquipmentUsage` entity/migration, new delete endpoints (workforce/equipment/activity), new update+delete endpoints (media/attachment), new `MaterialRepository`/`PurchaseRequestInvoiceRepository` date-range finders, new "materials by date"/"invoices by date" read endpoints on `DailyReportController`, approval display-name resolution, `DailyReportPdfService` redesign. `pantheon-web` — `DailyReportDetailView.vue` full redesign (global save, drag-drop, all sections). `pantheon-mobile` — `daily_report_detail_screen.dart` redesign plus net-new sections it never had (equipment usage, occurrences stay as-is/unchanged, materials-from-PR, attachments) to reach parity with web.
- **Data migration**: `DailyReportEquipmentUsage.equipment_id` nullable + new `custom_name` column (additive, no data loss).
- **Not touched**: `DailyReportMaterialReceived` (kept exactly as-is, per explicit decision), `DailyReportSignature` backend (kept, just unused by the UI), `DailyReportOccurrence`/"Ocorrências" (not mentioned in the redesign request — stays functionally as-is, only re-styled to match the new card language).
