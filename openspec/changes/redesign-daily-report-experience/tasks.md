## 6. Backend: approval display names + PDF redesign

- [x] 6.1 Added `DailyReportService.resolveApprovalDeciderNames`/`displayNameForMembership` (mirrors `PurchaseRequestPdfService`'s private helpers field-for-field) plus a new public `DailyReportService.listApprovalResponses(reportId)` that batches the resolution and returns fully-populated `DailyReportApprovalResponse`s (new `decidedByName` field, `null` for a still-`PENDING` step). **Decision**: extracted into `DailyReportService` rather than duplicating into `DailyReportPdfService` too (design.md left this as "extracted or duplicated") — both classes already live in the same package and the PDF service already needed a `DailyReportService` dependency for nothing to do with this, so a second independent copy would only risk the API and the PDF disagreeing on a name. `getDetail()` now calls `listApprovalResponses` instead of mapping `DailyReportApprovalResponse::from` directly. Caught and fixed a real bug here during testing: `resolveApprovalDeciderNames` returned `Map.of()` for the no-decided-steps case, and `Map.of().get(null)` throws `NullPointerException` (immutable maps reject null-key lookups) — a report with only `PENDING` steps hit this every time. Fixed by short-circuiting the lookup when `decidedBySiteMembershipId` is null instead of relying on the map to handle it.
